# 米粿Studio 管理后台产品与技术方案

> 状态：P1 方案稿，供确认后实施。当前不写入真实模型密钥，不改变线上积分或供应商配置。

## 1. 目标与边界

管理后台服务于米粿Studio平台运营人员，不与创作者工作台混在同一导航。首期必须回答四个问题：

1. 每个组织还有多少可用积分，积分从哪里来、花到哪里去？
2. 每个账号正在做什么、使用了多少、是否异常？
3. 各阶段与各供应商的任务成功率、耗时和失败原因如何？
4. 当前负责理解用户意图和编排任务的主模型是哪一版，是否健康，能否安全发布与回滚？

首期不包含企业结算开票、自动充值、复杂套餐、SSO/SCIM 或任意第三方插件市场。组织自己的管理页面与平台管理后台权限分离。

## 2. 推荐的信息架构

```text
管理概览
├── 组织
│   └── 组织详情：概览 / 成员 / 积分账本 / 使用情况 / 策略
├── 账号
│   └── 账号详情：组织关系 / 使用情况 / 任务 / 安全
├── 任务运营
│   └── 任务详情：谱系 / 调用 / 成本 / 错误 / 恢复
├── 积分中心
│   ├── 组织账户
│   ├── 账本流水
│   └── 待核对费用
├── 模型控制台
│   ├── 主模型部署
│   ├── 供应商连接
│   ├── 能力路由
│   └── 测试与发布记录
└── 审计日志
```

管理概览只放需要立即行动的信号：积分不足、未知费用冻结、成功率下降、队列积压、供应商异常和未完成的模型发布。详细分析在二级页面完成。

## 3. 角色与授权

平台权限与组织权限必须分开：

| 角色 | 范围 | 关键权限 |
|---|---|---|
| Platform Owner | 全平台 | 管理平台管理员、密钥主控、紧急回滚 |
| Platform Admin | 全平台 | 组织、账号、额度、任务、模型配置 |
| Finance Operator | 全平台财务 | 充值、调账、账本和对账；不能读模型密钥 |
| Support Operator | 全平台支持 | 只读组织/账号/任务；不能调账或发布模型 |
| Organization Owner/Admin | 单组织 | 成员、组织预算和本组织明细；不能进入平台模型控制台 |

模型密钥与大额调账属于高风险操作。生产版需要管理员重新验证身份；推荐再加 MFA。所有写操作继续使用 HttpOnly 会话、CSRF、幂等键和追加式审计事件。

## 4. 指标口径

### 4.1 积分

组织共享的是平台积分账户，不是供应商 API Token。使用整数最小单位（例如 `milli_point`），禁止用浮点数作为账本金额。

```text
账面余额 = grant + adjustment_credit - settled - adjustment_debit
已预占   = 尚未结算的 reserve
待核对   = unknown outcome 对应的 hold_unknown
可用积分 = 账面余额 - 已预占 - 待核对
```

流水类型：`grant`、`reserve`、`settle`、`release`、`hold_unknown`、`reconcile`、`adjust_credit`、`adjust_debit`、`expire`。任何人工调账都要求原因、操作者、幂等键和关联凭证；旧流水不可编辑或删除，只能以反向流水修正。

### 4.2 任务成功率

不能只展示一个“成功率”，后台至少区分：

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 技术成功率 | succeeded / (succeeded + failed) | 供应商与系统稳定性 |
| 首次成功率 | 第一次尝试成功的输入快照 / 已终结输入快照 | 返工与重试压力 |
| 最终成功率 | 两次受控尝试内成功 / 已终结输入快照 | P0/P1 交付能力 |
| 采用率 | 被提升为当前版本的候选 / 成功候选 | 结果可用性代理指标 |
| 返工率 | 带“不满意”意见的新尝试 / 已采用结果 | 创作质量与需求理解 |

分母排除 `queued`、`running` 和用户主动取消的 `cancelled`。结果不确定的真实调用单列为“待核对”，不能算作普通失败或自动重试。按阶段、供应商、模型配置版本、组织和账号均可切片。

### 4.3 使用情况

- 米粿图像任务：阶段、调用次数、成功/失败、积分、耗时、重试和待核对。
- 主模型 Agent 调用：输入 token、缓存 token、输出 token、请求数、耗时、供应商成本和配置版本。
- 业务产出：批次数、漫画格数、采用版本数、提交到组织数和导出数。

所有调用时间使用 UTC 存储，界面按用户时区显示。概览使用日汇总表，任务详情读取原始事件，避免大表实时聚合拖慢后台。

## 5. 数据模型

### 5.1 组织与账号

```text
organizations
  id, name, slug, status, plan_code, timezone, created_by, created_at

organization_memberships
  organization_id, user_id, role, status, joined_at, left_at

projects
  id, organization_id, name, status, producer_user_id
```

新增 `users.platform_role`，旧 `users.role` 只做迁移期兼容；组织角色必须放在 membership 上。`batches` 增加可空的 `organization_id`、`project_id`；旧批次仍由 `owner_user_id` 私有，不做破坏性归属推断。

### 5.2 任务与归因

现有 `run_attempts` 增加提交时冻结的：

```text
organization_id, actor_user_id, project_id, capability,
provider_connection_id, deployment_revision_id, reserved_ledger_entry_id
```

不能在报表时通过当前 membership 反推历史组织，因为成员可能转组或离职。

主模型使用独立的 `agent_runs`：

```text
id, organization_id, actor_user_id, task_id, capability,
provider_connection_id, deployment_revision_id, model_id,
status, input_tokens, cached_input_tokens, output_tokens,
provider_cost_microunits, billed_points_milli,
latency_ms, provider_request_id, client_request_id,
error_code, created_at, finished_at
```

图像生产任务和 Agent 推理调用可以通过 `task_id` 关联，但不要共用一套状态字段或成本单位。

### 5.3 积分账本

```text
credit_accounts
  id, organization_id UNIQUE, currency, status, version

credit_transactions
  id, account_id, transaction_type, task_id, run_attempt_id,
  usage_user_id, actor_user_id, reason, external_reference,
  idempotency_key, created_at

credit_ledger_entries
  id, transaction_id, bucket, amount_milli
  bucket ∈ available / reserved / held / spent / external
```

每笔 transaction 的所有 entry 金额相加必须为零，形成可校验的双向账本。例如 `grant` 为 `external -N / available +N`，`reserve` 为 `available -R / reserved +R`。任何余额都由 entries 汇总得出，不维护可直接覆盖的余额字段。

“额度检查 + reserve 流水 + 任务入队”必须位于同一数据库事务。成功后 `settle`，明确未调用则 `release`，结果未知则 `hold_unknown` 并阻止自动重试。

### 5.4 日汇总

`usage_daily_rollups` 按 `date + organization + user + capability + provider + deployment_revision` 聚合调用数、状态数、积分、token 和延迟直方图。原始表是真相，汇总表可重建。

## 6. 主模型配置

### 6.1 为什么不能只有三个可随时覆盖的字段

后台表单可以突出 `Base URL`、`API Key` 和 `模型型号`，但运行时必须使用不可变配置版本。直接覆盖当前值会使历史任务无法解释，也无法快速回滚。

推荐实体：

```text
provider_connections
  id, name, protocol, base_url, allowed_host,
  secret_ref, key_fingerprint, status, last_probe_at

model_deployment_revisions
  id, connection_id, model_id, reasoning_effort,
  max_output_tokens, timeout_ms, default_parameters_json,
  prompt_policy_version, status, created_by, created_at

capability_routes
  capability, active_revision_id, fallback_revision_id,
  rollout_percent, updated_by, updated_at
```

首期协议建议只开放：

- `openai_responses`：主模型的首选协议；
- `openai_compatible_responses`：明确通过兼容性测试的受控供应商；
- 后续再加 `openai_chat_legacy`，不要让遗留协议成为默认。

OpenAI 官方建议 API key 仅在服务端环境变量或密钥管理服务中加载，不能出现在浏览器代码。Responses API 适用于推理、工具调用和多轮工作流；生产调用应保留供应商 `x-request-id`，并发送内部 `X-Client-Request-Id` 以支持故障追踪。

### 6.2 密钥和 Base URL 安全

- API key 使用密钥管理服务或由独立主密钥进行 envelope encryption；数据库只存 `secret_ref`、后四位指纹和版本。
- API 永不返回明文密钥；留空表示保持现有密钥，只有显式“替换密钥”才写新版本。
- UI 不使用 `localStorage`、URL、日志或分析事件保存密钥。
- Base URL 只允许 HTTPS；解析 DNS 后拒绝 loopback、链路本地、内网和云元数据地址。
- 平台维护允许的主机清单。自定义主机必须由 Platform Owner 审批，重定向后也重新校验。
- 探测接口限制响应体、超时和重定向，防止 SSRF 与大响应耗尽资源。

### 6.3 草稿、测试、发布与回滚

```text
草稿 → 结构校验 → 连通性测试 → 受控样例评测 → 待发布 → 生效
                                                    ↓
                                                  回滚
```

连通性测试优先调用模型读取接口；会产生费用的真实推理测试必须明确显示成本上限并再次确认。发布采用原子指针切换，不改写旧 revision。所有新任务绑定生效时的 revision ID；在途任务不切换。回滚只把能力路由指回上一个已验证版本。

首期保留一个“默认主模型”路由，同时为以后按能力覆盖留出位置：`intent_understanding`、`task_planning`、`story_adaptation`、`character_design`、`storyboard`。没有覆盖时继承默认主模型。

### 6.4 推荐的初始策略

- 默认协议：Responses API。
- 默认主模型只作为平台级默认值，不硬编码在应用中。
- 意图理解与常规编排从中等 reasoning effort 起步，用代表性任务评测质量、延迟与 token 后再调。
- 复杂小说拆解可使用更强的能力路由，批量轻任务可用成本更低的路由。
- 对终端用户请求发送稳定、隐私保护的 `safety_identifier`，不要直接发送邮箱或用户 ID。

## 8. 后台页面规格

### 概览

- KPI：活跃组织、活跃账号、组织可用总积分、7日技术成功率、待核对积分。
- 7/30日任务量与成功率趋势。
- 分阶段成功率和 P50/P95 耗时。
- 需要处理：低余额、未知费用、失败率突增、队列积压、模型连接失效。

### 组织详情

- 基本状态、套餐、时区、成员数、项目数。
- 可用/预占/待核对积分及最近流水。
- 按成员、项目、阶段、供应商的使用分布。
- 月预算、成员限额、真实供应商使用角色和低余额阈值。

### 账号详情

- 邮箱、状态、最近登录、平台角色、组织 memberships。
- 7/30日任务数、积分、成功率、返工率和最近失败。
- 禁用账号时撤销其会话，但保留历史归因。

### 任务运营

- 按时间、组织、账号、能力、阶段、供应商、模型 revision、状态筛选。
- 列表显示技术状态、耗时、积分/token、重试和错误码。
- 详情显示 trace/request ID、输入/输出版本 ID、账本流水和恢复决策，不直接展示敏感正文。

### 模型控制台

- 当前默认主模型和健康状态。
- 连接列表：协议、Base URL 主机、密钥指纹、最后探测。
- 部署版本：模型、参数、评测结果、发布人和时间。
- 能力路由与回退版本。
- “新建草稿”“测试连接”“发布”“回滚”四个动作清晰分离。

## 9. 分阶段实施

### P1-Admin A：只读运营后台

- 管理后台独立路由和 Platform Admin 门控；
- 组织/账号基础表；
- 现有任务的只读指标与失败归因；
- 模型配置静态草稿与审计表，不执行真实调用。

历史 P0 任务标记为 `legacy/unattributed`：可以参与系统稳定性分析，但不能通过当前批次 owner 反推为精确组织账单。现有 Mock 与 `estimate` 成本不自动扣减任何组织账户。当前前端自动提升候选，因此历史 promote 也不能冒充用户接受率。

### P1-Admin B：组织积分账本

- 整数追加式账本；
- 原子预占、结算、释放和未知费用冻结；
- 组织与账号额度策略；
- 调账双确认与审计。

### P1-Admin C：主模型配置

- 服务端密钥存储；
- OpenAI Responses 协议适配；
- 探测、受控评测、发布、灰度和回滚；
- Agent 调用 token/成本/延迟追踪。

### P1-Admin D：生产化

- PostgreSQL、对象存储与独立 Worker；
- MFA、告警、备份、数据保留与灾难恢复；
- 组织管理员自助页面与企业能力。

SQLite 可用于单机小规模试点，但在多组织、多 Worker 或财务级共享账本启用前，应迁移 PostgreSQL。正式启用扣费前先运行一段时间 shadow ledger，对比任务事实与账本结果，确认预占、结算、释放和未知冻结均可重放且守恒。

## 10. 确认点

进入后端实现前建议确认：

1. 平台积分是充值余额、套餐额度，还是两者并存；是否过期。
2. 组织 Owner 能否自行给成员设置限额，还是只能平台管理员操作。
3. “成功率”首屏默认展示技术成功率还是最终成功率；本方案推荐技术成功率并同时展示首次成功率。
4. 主模型 Base URL 是否只接受批准供应商；本方案强烈不建议允许任意公网 URL 直接生效。
5. 模型发布是否要求双人审批；本方案建议正式扣费环境开启。
