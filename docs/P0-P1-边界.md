# P0 与后续阶段边界

## 当前 P0 的承诺

P0 是内部可行性样片工具，不是完整产品。它只承诺验证以下闭环：

```text
单格草稿批量导入
  → 勾线候选
  → 人工选定
  → 底色候选
  → 人工选定
  → 光影候选
  → 人工选定
  → 固定 2×2 PNG 与 JSON 清单
```

| 项目 | P0 当前范围 |
|---|---|
| 使用对象 | 带应用账号隔离的内部/邀请制 MVP 用户 |
| 输入 | 已切好的单格 PNG、JPEG、WebP，一格一图 |
| 处理 | 勾线、底色、光影三个明确阶段 |
| 供应商 | 默认模拟；受双安全门保护的米粿 MCP |
| 版本 | 候选不覆盖旧图；人工选定；旧版可恢复；下游可标记过期 |
| 失败处理 | 单项重试；每格每阶段同一输入最多两次尝试 |
| 存储 | 本地 SQLite 和本地文件目录 |
| 排版 | 固定 2×2、居中适配、不裁切 |
| 输出 | PNG 页面、JSON 布局清单、任务与成本记录 |

## P0 明确不做

- 小说、DOCX 或 EPUB 导入；
- 故事圣经、人物关系、时间线和角色不同时期造型；
- 自动脚本、文字分镜、画面分镜和外接生图模型；
- 圈选局部、蒙版、只改手或脸的区域返工；
- 气泡、对白、拟声词、字体和专业植字；
- 自由拖拽排版、条漫长图或固定页模板编辑器；
- PSD 分层生产交付；
- 组织内多人协作、评论、交接、审批流和通知；
- 组织积分账本、企业计费、额度、SLA 和多组织租户；
- 可由用户任意填写的模型 Base URL；
- GPT-5.6、GPT Image 2 或其他模型的管理后台；
- 生产级云存储、灾难恢复、跨机器 Worker 和高并发。

这些能力没有出现在界面，不应通过临时脚本或人工流程包装成“已经支持”。

## 进入 P1 的前提

只有 P0a 的质量、人工时间、稳定性和成本门槛全部通过，并且米粿商业与数据条件得到确认，才进入 P1。

P1 的重点是把已经证明有效的批量后期闭环变成内部生产 MVP：

- 更完整的批量任务、筛选、取消和审阅体验；
- 正式版本树、任务账本和审计；
- 可靠对象存储与数据库；
- PNG、WebP、分层包和简单纵向条漫模板；
- 管理员可配置的受控供应商、模型、密钥、路由和健康检查；
- 组织、成员角色、提交/接手工作流和基础监控；
- 共享积分的预占、结算、释放和审计账本。

P1 仍不等于“小说到整部漫画”。当前注册、登录和个人批次隔离已经提前成为 MVP 基线，但不代表组织协作已经完成。组织协作按 [B 端组织协作设计](B端组织协作设计.md) 分阶段进入；局部返工和专业排版属于 P2，小说改编、角色 Canon、分镜与外接生图属于 P3，完整商业化多租户属于 P4。

## 最终效果的正确预期

P0 成功的标志不是每张图一次生成就完美，而是：

- 大多数代表性格子在受限次数内得到可进入下一工序的结果；
- 人可以看懂每一步发生了什么，并主动决定采用哪个版本；
- 修改一个格子不会破坏整批作品；
- 失败、重启和恢复不会导致不可追踪的重复调用；
- 实际人工返工时间和真实积分成本足以支持继续投资。

如果这些条件没有成立，应保留评测数据并停止扩建，而不是先实现小说、分镜、排版和管理后台来掩盖核心图像链路的问题。
